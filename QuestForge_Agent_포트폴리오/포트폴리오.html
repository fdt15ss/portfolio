QuestForge Agent

플레이어의 현재 게임 상태를 보고 생산·납품·탐험 퀘스트를 만들어 주는 AI Agent입니다. 퀘스트의 숫자(목표 아이템, 수량, 보상, 완료 조건, 마감 시간)는 서버 규칙이 정하고, LLM은 제목과 설명 문장만 다듬도록 역할을 나눴습니다.

FastAPI WebSocket 서버가 요청을 받고, LangGraph 파이프라인이 라우팅 → 검색 → LLM 호출 → 검증 → 대체(fallback) 과정을 처리합니다. React로 만든 테스트 화면 Quest Lab에서 조건을 바꿔 가며 결과와 처리 경로(Agent Trace)를 함께 확인할 수 있습니다.

숫자는 서버가, 문장은 LLM이

서버가 CSV 규칙으로 완성된 퀘스트 초안(draft)을 먼저 만들고, LLM에게는 제목·설명·생성 이유만 받습니다. LLM 답변을 합칠 때도 목표·보상·완료 조건 같은 서버 필드는 덮어쓰지 않아서, 모델이 엉뚱한 답을 해도 게임 규칙은 그대로 유지됩니다.

🔄

실패 경로까지 그래프로 정의

요청 검증 → 라우팅 → 캐시 → LLM 호출(3단계 모델 순서) → 스키마 검증 → 대체 생성 → 응답을 LangGraph 노드로 나눴습니다. 생산·납품·탐험 하위 Agent도 각각 별도의 LangGraph 그래프로 구현했습니다.

재현하고 추적할 수 있게

가짜 LLM(StubLLM)으로 빈 응답·잘못된 JSON·스키마 위반 같은 실패를 외부 API 없이 재현해 테스트합니다. 응답 metadata에는 선택된 Agent, 사용한 모델, LLM 시도 기록, 대체 생성 여부와 원인을 남깁니다.

왜 LLM에게 퀘스트 전체를 맡기지 않았나

가장 간단한 방법은 게임 상태를 프롬프트에 넣고 퀘스트 JSON 전체를 LLM이 만들게 하는 것입니다. 실제로 처음에는 그렇게 만들었지만, 필드 누락이나 존재하지 않는 아이템 같은 문제가 반복됐습니다(아래 시행착오 1). 그래서 다음처럼 역할을 나눴습니다.

항목 LLM이 전부 만드는 방식 QuestForge 방식
수량 플레이 상황과 맞지 않는 수량이 나올 수 있음 인벤토리·진행 단계·메인 퀘스트를 바탕으로 서버가 규칙대로 계산
보상 게임에 없는 아이템이 보상에 들어갈 수 있음 quest_reward_rules.csv 기준으로 서버가 계산하고 LLM은 수정 불가
응답 형식 필드 누락·형식 오류 시 전체 응답이 실패 서버 draft를 먼저 만들고, Pydantic 스키마 검증 + draft에 있는 퀘스트 id만 병합
LLM 장애 LLM이 실패하면 퀘스트를 만들 수 없음 모델 3개를 순서대로 시도(default → fallback1 → fallback2)하고, 모두 실패하면 서버 draft로 대체
LLM의 역할 규칙 계산과 JSON 생성까지 전부 제목, 설명, 생성 이유, 메인 퀘스트와의 연결 이유 작성

시스템 구조와 처리 흐름

Quest Lab이 보낸 WebSocket 요청은 LangGraph 파이프라인의 노드를 순서대로 거쳐 응답으로 돌아옵니다. 중간에 실패하면 정해진 대체 경로나 오류 응답으로 빠집니다.

1. Quest Lab 요청
인벤토리, 해금 장비·레시피, 최근 이벤트, 메인 퀘스트, 탐험 후보지를 담아 agent.request 메시지를 보냅니다. 화면에서 입력한 한글 이름(예: 철광석)은 보내기 전에 내부 ID(resource_iron_ore)로 바뀝니다.
2. WebSocket 서버
FastAPI의 /ws/agent 엔드포인트가 메시지를 받아 JSON을 해석하고 파이프라인을 실행합니다. JSON이 깨져 있으면 INVALID_JSON 오류를 바로 돌려줍니다.
3. 검증 · 라우팅
메시지 형식을 검증한 뒤, LLM이 처리할 Agent를 선택합니다(현재는 quest_generator). 퀘스트 생성 Agent는 요청한 개수에 맞춰 생산·납품·탐험 하위 Agent의 결과를 조합합니다.
4. 캐시 확인
같은 조건의 요청이 이미 있으면 메모리 캐시의 결과를 재사용해 LLM 생성을 건너뜁니다. 이때 마감 시간(expires_at)만 현재 시각 기준으로 다시 계산합니다.
5. 데이터 검색
자원·레시피·보상 규칙은 CSV에서 정확히 조회하고, 시나리오와 분위기에 맞는 참고 문서는 ChromaDB 유사도 검색으로 찾아 프롬프트에 넣습니다.
6. 서버 draft 생성
목표 아이템, 수량, 보상, 완료 조건, 마감 시간이 모두 채워진 그대로 써도 되는 퀘스트 초안을 서버가 먼저 만듭니다.
7. LLM 보강 · 검증
LLM에게 제목·설명만 받아 Pydantic 스키마와 퀘스트 id를 검증한 뒤 draft에 합칩니다. 실패하면 다음 모델로 넘어가고, 세 모델이 모두 실패하면 draft를 그대로 응답합니다(원인은 metadata에 기록).

Quest Lab 기본 입력값으로 실제 전송되는 요청입니다(일부 필드 생략). 응답의 metadata에는 처리 경로가 기록됩니다.

실제 실행 화면

로컬 PC에서 백엔드와 Quest Lab을 실행하고, 로컬 LLM(Ollama gemma4:e2b)으로 실제 요청을 보내 캡처한 화면입니다. 이미지를 누르면 크게 볼 수 있습니다.

캡처일: 2026-11-14 · 입력값: Quest Lab 기본값(생산·납품·탐험 각 1개, 일일·주간·돌발 각 1개)

1. Quest Lab 전체 화면

왼쪽에서 도메인별·타입별 생성 개수와 돌발 퀘스트 제한 시간(30분~4시간)을 정하고, 인벤토리·메인 퀘스트 같은 게임 상태를 입력합니다. 퀘스트 생성을 누르면 WebSocket으로 요청이 전송되고, 오른쪽에 결과 카드가 표시됩니다. 결과는 localStorage에 저장돼 새로고침해도 유지됩니다.

2. 도메인별 퀘스트 카드와 완료 방식

생산·납품 퀘스트는 objective_count 방식이라 수량 진행도(0 / 6)와 +1 / 채우기 버튼으로 완료를 시험합니다. 탐험 퀘스트는 manual 방식이라 수량 대신 방문 완료 버튼이 나옵니다(시행착오 2). 각 카드에는 남은 시간, 메인 퀘스트 "장거리 신호 복구"와의 연결 이유, 서버가 계산한 보상(xp·credits·자원)이 함께 표시됩니다.

남은 문제: 작은 로컬 모델(gemma4:e2b)을 쓰면 납품 카드 제목처럼 resource_iron_ore 같은 내부 ID가 문장에 섞이는 경우가 아직 있습니다. 목표·수량·보상은 서버 값이라 정확하지만, 문장 품질은 모델 성능에 영향을 받습니다.

objective_count manual expires_at main_quest_link

3. Agent Trace — LLM 응답이 실패해 서버 draft로 대체된 실제 사례

이 요청에서는 로컬 모델의 답변이 검증을 통과하지 못했습니다. 파이프라인은 오류를 내지 않고 서버 draft로 대체해 퀘스트를 정상 반환했고, Trace에는 Fallback: yes, 원인 invalid_llm_response, 소요 시간(15,372ms)이 남았습니다.

Trace 패널은 선택된 Agent, 사용 모델, 대체 여부와 원인, 클라이언트에서 잰 소요 시간을 보여 주고, 아래에 원본 metadata를 그대로 표시합니다. 옆 패널에서 보낸 요청 JSON과 받은 응답 JSON을 확인하고, JSON 가져오기 / 현재 JSON 복사로 같은 조건을 다시 재현할 수 있습니다.

fallbackReason llmAttempts selectedLeafAgent JSON 재현

인벤토리·해금 장비·해금 레시피를 직접 타이핑하지 않고 목록에서 고를 수 있습니다. 목록은 게임 데이터 CSV에서 읽어 오며, 한글 이름과 내부 ID를 함께 보여 줍니다. 직접 입력할 때도 quest_input_aliases.csv의 별칭(예: "철광석")을 내부 ID로 바꿔서 서버에 보냅니다.

개발 중 겪은 시행착오와 해결 과정

프로젝트를 진행하며 실제로 부딪힌 문제 네 가지와, 그때 구조를 어떻게 바꿨는지 정리했습니다.

시행착오 1. LLM이 퀘스트 JSON 전체를 만들면서 형식이 자주 깨짐

해결: 생성 순서 변경
⚠️ 문제

처음에는 LLM에게 QuestResponse JSON 전체(목표, 수량, 완료 조건, 보상)를 만들게 했습니다. 로컬 모델에서 목표가 비어 있거나, 정의되지 않은 완료 조건 값이 오거나, CSV에 없는 아이템이 보상에 들어가는 일이 반복됐습니다. 퀘스트 5개 중 1개만 틀려도 전체 응답이 검증에 실패했습니다.

원인은 모델 성능이 아니라 역할 분배였습니다. 서버가 계산할 수 있는 값까지 LLM에게 맡긴 구조였고, 프롬프트를 길게 써도 실패 확률이 줄 뿐 없어지지는 않았습니다.

✅ 해결
  1. 서버가 CSV와 게임 상태로 완성된 퀘스트 draft를 먼저 만듭니다.
  2. LLM 응답은 quest_plan / quest_text_updates 형식으로 줄여 제목·설명·이유만 받습니다.
  3. 병합 함수가 병합 전후로 두 번 스키마를 검증하고, draft에 없는 id가 오면 거부합니다. 빈 문자열은 무시하고 draft 값을 유지합니다.
  4. 병합에 실패하면 그 단계만 서버 draft로 대체하고, 원인을 metadata에 남깁니다.
💡 배운 점: LLM이 규칙을 어겼는지 나중에 검사하는 것보다, 처음부터 규칙 필드를 LLM에게 넘기지 않는 구조가 더 확실했습니다.

시행착오 2. 탐험 퀘스트가 "0 / 1" 수량 목표로 표시됨

해결: 완료 방식(mode) 분리
⚠️ 문제

탐험 퀘스트도 생산 퀘스트와 같은 objective_count(수량 세기) 방식을 그대로 썼습니다. 그래서 "약한 구조 신호 조사"가 "0 / 1"처럼 표시됐고, 탐험은 아이템을 모으는 게 아니라 장소에 가는 행동이라 이 숫자를 올릴 방법이 없었습니다.

도메인마다 응답 형식을 따로 만들면 WebSocket 계약과 화면 코드가 세 갈래로 나뉩니다. 실제로 달라야 하는 건 완료 판정 방식 하나뿐이었습니다.

✅ 해결
  1. 공통 스키마는 유지하고, 완료 조건에 mode 값(objective_count / manual)을 추가했습니다.
  2. 탐험 Agent는 manual과 함께 행동 문구를 만듭니다. 타입별로 "방문 완료"(일일), "탐험 기록 완료"(주간), "이상 징후 조사 완료"(돌발)로 달라집니다.
  3. 탐험 대상은 요청의 탐험 후보지 → 최근 이벤트 → 메인 퀘스트 → CSV 시나리오 순서로 채워, 입력이 비어도 목표가 생깁니다.
  4. Quest Lab은 mode만 보고 진행도 바 또는 완료 버튼을 그립니다.
💡 배운 점: 스키마를 통째로 나누기보다 정말 달라지는 축 하나만 분리하니, 계약·캐시·검증 코드를 그대로 재사용하면서 확장할 수 있었습니다.

시행착오 3. 내부 ID가 문장에 노출되고, 납품 목표가 플레이와 무관함

개선: 판단용 데이터 분리 · 인벤토리 기반 목표
⚠️ 문제
  • equipment_miner_machine 같은 내부 ID가 사용자 문장에 그대로 나왔습니다. 게임 상태를 프롬프트에 문장처럼 이어 붙여서 LLM이 그 표기를 따라 썼습니다.
  • 납품 퀘스트가 인벤토리에 없는 철괴를 기본 목표로 잡았고, 수량도 5, 6, 7처럼 순번을 더한 값이라 실제 보유량과 상관이 없었습니다.
✅ 해결
  1. 게임 상태는 판단용 데이터로 넘기고, 화면에 보일 이름은 CSV 별칭으로 연결했습니다. 이름을 코드에 하드코딩하지 않아 CSV만 고치면 됩니다.
  2. 납품 대상은 요청에 지정된 아이템을 우선하고, 없으면 보유량이 0보다 큰 인벤토리 자원 중에서 고릅니다.
  3. 수량은 타입별 비율로 계산합니다: 돌발 5%(최소 1), 일일 10%(최소 2), 주간 25%(최소 5). 계산값이 보유량을 넘지 않도록 제한합니다.
💡 배운 점: 납품 목표는 "지금 창고에 있는 것 중 타입에 맞는 비율만큼"이라는 규칙으로 플레이와 연결됐습니다. 다만 위 실제 화면 2처럼 작은 로컬 모델에서는 ID 노출이 줄었지만 완전히 없어지지는 않아, 남은 과제로 두고 있습니다.

시행착오 4. 캐시에서 꺼낸 퀘스트의 마감 시간이 이미 지나 있음

해결: 시간 필드만 다시 계산
⚠️ 문제

같은 조건의 요청은 캐시된 응답을 그대로 돌려줬는데, 이때 generated_at, expires_at도 처음 만든 시각 그대로였습니다. 제한 2시간짜리 돌발 퀘스트를 3시간 뒤에 다시 요청하면, 받자마자 이미 만료된 퀘스트가 왔습니다.

캐시를 끄면 해결되지만 LLM 호출 비용과 대기 시간이 다시 늘어납니다. 문제는 캐시 안에 재사용해도 되는 값(제목·목표·보상)과 요청 시각에 따라 달라지는 값(시간)이 섞여 있다는 점이었습니다.

✅ 해결
  1. 캐시 hit 경로에서 결과를 복사한 뒤 마감 시간만 다시 계산합니다.
  2. 계산 규칙은 새로 생성할 때와 같은 함수를 씁니다: 일일은 다음 자정, 주간은 다음 월요일 자정, 돌발은 지금 + 제한 시간(한국 시간 기준).
  3. 돌발 제한 시간은 1분~24시간 범위로 보정해 이상한 값이 들어가지 않게 했습니다.
  4. 회귀 테스트 2개로 "시간은 갱신되고, 나머지 필드는 바뀌지 않는다"를 함께 검증합니다.
💡 배운 점: 캐시를 켜거나 끄는 두 가지 선택만 있는 게 아니었습니다. 값의 성격을 나눠 시간에 의존하는 값만 응답 직전에 계산하니 비용과 정확성을 둘 다 챙길 수 있었습니다. (실제 화면 캡처 중에도 같은 요청을 다시 보냈을 때 내용은 그대로이고 generated_at만 새 시각으로 바뀌는 것을 확인했습니다.)

기술 선택 이유

🐍 FastAPI + Pydantic

WebSocket 엔드포인트를 간단히 만들 수 있고, Pydantic 모델로 요청·응답·퀘스트 스키마를 코드 하나로 정의하고 검증할 수 있습니다.

🕸️ LangGraph

"실패하면 다음 모델 → 그래도 실패하면 draft" 같은 분기를 if문 덩어리가 아니라 노드와 엣지로 드러낼 수 있어, 흐름을 읽고 테스트하기 쉽습니다.

📊 CSV + ChromaDB

정확해야 하는 수치·규칙은 CSV에서 그대로 읽고, 문장 분위기에 필요한 맥락만 ChromaDB 유사도 검색으로 보충합니다.

⚛️ React + TypeScript + Vite

요청 조건 입력, 한글 별칭 변환, WebSocket 송수신, 퀘스트 카드와 Agent Trace 표시를 하나의 테스트 화면으로 만들었습니다.

📦 uv

uv.lock으로 의존성 버전을 고정해, 다른 PC에서도 uv sync 한 번으로 같은 환경을 만들 수 있습니다.

🧪 pytest + Vitest

백엔드는 계약·시나리오·경계값 테스트, 프론트엔드는 요청 변환과 화면 동작 테스트로 나눠 변경 후 회귀를 확인합니다.

현재 한계와 다음 단계

현재 한계: 서버 draft 대체는 LLM이 Agent를 선택한 이후의 생성 단계를 보호합니다. 맨 처음 Agent 선택(라우팅)에 쓸 LLM이 모두 실패하면, 서버는 임의로 Agent를 고르지 않고 ROUTING_UNAVAILABLE 오류를 반환합니다. 즉 "LLM이 전혀 없어도 항상 퀘스트가 나온다"는 구조는 아닙니다. 또한 작은 로컬 모델에서는 문장에 내부 ID가 섞이는 경우가 남아 있습니다.

1. LLM 없이도 라우팅

요청에 유효한 agent가 명시돼 있으면 LLM 라우팅을 건너뛰어, LLM이 전부 실패해도 draft 대체까지 도달하도록 개선합니다.

2. 문장 품질 자동 검사

LLM이 쓴 제목·설명에 내부 ID가 섞였는지 검사해, 섞였으면 draft 문장으로 되돌리는 검증을 추가합니다.

3. 퀘스트 이력 저장과 밸런스 리포트

서버 DB에 플레이어별 퀘스트·완료 기록을 저장해 개인화에 쓰고, 완료율·소요 시간·보상 가치를 모아 밸런스를 점검합니다.

4. 게임 클라이언트 연동

지금의 agent.request WebSocket 계약을 그대로 사용해 Unreal 등 실제 게임 클라이언트와 연결합니다.
